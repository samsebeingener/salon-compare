# streamlit-ui Specification

## Purpose

Опциональная визуализация точек разбора на карте Яндекс в Streamlit: expander в отчёте, два viz-ключа, координаты из 2ГИС или серверный геокод. Не влияет на сбор полей, scoring и SQLite payload.

## Requirements

### Requirement: Опциональная карта Яндекс в expander отчёта
После сбора трёх точек или открытия сохранённого разбора интерфейс SHALL показать свёрнутый по умолчанию expander «Карта (Яндекс JS API, только просмотр)» с подписью, что блок не влияет на сбор полей и индекс. Без `YANDEX_MAPS_JS_API_KEY` система MUST показать подсказку добавить ключ и MUST NOT падать. Таблица, карточки, индекс и вывод модели SHALL работать независимо от наличия карты.

#### Scenario: Нет JS-ключа
- GIVEN разбор с тремя точками и пустой `YANDEX_MAPS_JS_API_KEY`
- WHEN пользователь открывает отчёт
- THEN expander карты есть
- THEN внутри подсказка про `YANDEX_MAPS_JS_API_KEY`
- THEN таблица полей видна

#### Scenario: Карта с координатами 2ГИС
- GIVEN три точки с заполненными `map_lat` и `map_lon` из 2ГИС и валидный `YANDEX_MAPS_JS_API_KEY`
- WHEN пользователь раскрывает expander
- THEN отображается HTML-виджет карты с метками
- THEN подпись «Меток на карте: N из N»

### Requirement: Два отдельных ключа Яндекса для визуализации
Система SHALL читать `YANDEX_MAPS_JS_API_KEY` только для подгрузки JavaScript API карт в браузере. Система SHALL читать `YANDEX_GEOCODER_API_KEY` только для серверного HTTP-геокода адреса или названия, если у точки нет `map_lat` / `map_lon`. Один ключ MUST NOT подменять другой. Система MUST NOT использовать `YANDEX_MAPS_API_KEY` (ключ сбора Places, удалён в `drop-yandex-maps-source`).

#### Scenario: Разные env-переменные
- GIVEN `YANDEX_MAPS_JS_API_KEY=js-key` и `YANDEX_GEOCODER_API_KEY=geo-key`
- WHEN читают ключи из окружения
- THEN JS-ключ равен `js-key`
- THEN ключ геокодера равен `geo-key`

#### Scenario: Нужен геокодер, ключа нет
- GIVEN точка без `map_lat` / `map_lon`, но с адресом
- AND пустой `YANDEX_GEOCODER_API_KEY`
- WHEN раскрывают expander карты
- THEN предупреждение про отдельный ключ API Геокодера
- THEN метки с координатами 2ГИС всё равно могут отображаться

### Requirement: Координаты меток из 2ГИС или геокодера
Для каждой точки отчёта система SHALL взять `map_lat` и `map_lon` из собранной записи (источник — 2ГИС). Если координат нет, система MAY один раз запросить Geocoder API по адресу (с префиксом «Москва,» при необходимости), затем по названию салона. Геокод MUST выполняться на сервере (`geocode-maps.yandex.ru`), не в браузере. HTTP-клиент геокодера MUST использовать те же `httpx_client_kwargs` из `proxy.py`, что и остальные исходящие запросы каркаса (`trust_env` истина), MUST NOT отключать прокси окружения (`trust_env=False`). Система MUST NOT записывать результат геокода в payload SQLite и MUST NOT менять поля сбора.

#### Scenario: Координаты уже в записи
- GIVEN `map_lat=55.75` и `map_lon=37.62` из 2ГИС
- WHEN строят маркеры
- THEN HTTP-геокод не вызывается
- THEN метка использует эти координаты

#### Scenario: Геокод по адресу
- GIVEN пустые `map_lat` / `map_lon` и адрес «ул. Примерная, 1»
- AND валидный `YANDEX_GEOCODER_API_KEY`
- WHEN разрешают координаты меток
- THEN один запрос к Geocoder с текстом «Москва, ул. Примерная, 1»
- THEN координаты попадают только в HTML карты

#### Scenario: Геокодер уважает прокси окружения
- GIVEN запрос Geocoder API
- WHEN собирают kwargs HTTP-клиента для геокода
- THEN kwargs совпадают с `httpx_client_kwargs()` из `proxy.py`
- THEN `trust_env` истина

### Requirement: Карта не влияет на сбор и scoring
Модуль визуализации (`yandex_viz.py`) MUST NOT импортироваться из `collect`, `score`, `maps_http` или `resolver` для сбора полей. Вызовы API Яндекса в этом capability MUST ограничиваться отображением в Streamlit. Отсутствие ключей, ошибка геокода или пустая карта MUST NOT менять индекс, таблицу полей и сохранённый JSON разбора.

#### Scenario: Сбор без ключей Яндекса
- GIVEN пустые viz-ключи и валидный `TWOGIS_API_KEY`
- WHEN пользователь разбирает три зацепки
- THEN поля карт заполняются только из 2ГИС
- THEN индекс считается без участия Яндекса

#### Scenario: Карта не пишет в SQLite
- GIVEN успешный геокод для отображения
- WHEN сохраняют разбор в SQLite
- THEN в payload нет полей координат от Яндекса
- THEN `map_lat` / `map_lon` остаются как после сбора 2ГИС

### Requirement: Начальный viewport подгоняется под метки
HTML карты SHALL центрировать и масштабировать вид так, чтобы все поставленные метки были видны. Для одной метки система SHALL использовать увеличенный zoom (около 15). Для нескольких меток система SHALL вызвать `setBounds` коллекции с отступом и MUST NOT опускать zoom ниже минимального порога (13), если API позволяет. Без меток система SHALL показать сообщение вместо карты.

#### Scenario: Три метки в Москве
- GIVEN три точки с координатами в пределах города
- WHEN рендерят карту
- THEN в HTML есть `setBounds` для коллекции меток
- THEN начальный center — среднее координат меток

#### Scenario: Одна метка
- GIVEN одна точка с координатами
- WHEN рендерят карту
- THEN карта центрируется на этой точке с zoom около 15

#### Scenario: Нет координат после геокода
- GIVEN ни одна точка не получила lat/lon
- WHEN строят HTML
- THEN текст «Метки не поставлены» без падения приложения

### Requirement: Безопасная вставка данных 2ГИС в HTML карты
HTML карты MUST NOT содержать сырую последовательность `</script>` из `title` или `address` внутри executable JavaScript. Точки SHALL сериализоваться в JSON и вставляться через `<script type="application/json">` с чтением `JSON.parse` на клиенте (MUST NOT `const POINTS = {payload}` внутри JS). После `json.dumps` система SHALL экранировать `<`, `>`, `&` как `\u003c`, `\u003e`, `\u0026` и/или заменить `"</"` так, чтобы HTML-парсер не закрывал скрипт. Содержимое `balloonContentHeader` и `balloonContentBody` MUST быть HTML-экранировано через `html.escape` на сервере до свойств метки.

#### Scenario: Script breakout в названии
- GIVEN точка с названием, содержащим `</script>`
- WHEN строят HTML карты
- THEN в разметке нет сырой последовательности `</script>` из названия внутри JS
- THEN точки читаются из JSON (`application/json` и/или `JSON.parse`), а не из сырого `const POINTS = {payload}`

#### Scenario: img onerror в адресе балуна
- GIVEN точка с адресом `<img src=x onerror=alert(1)>`
- WHEN строят HTML карты
- THEN содержимое балуна HTML-экранировано (`html.escape`)
- THEN в HTML нет незаэскейпленного `<img src=x onerror=`

### Requirement: Баннер падения сбора точки
Если у записи точки `collect_ok` ложь, интерфейс MUST показать предупреждение вида «Сбор точки X упал», где X — заголовок точки. Система MAY показать краткое `collect_error`. Stack trace MUST NOT выводиться в UI. Таблица полей и остальные точки SHALL оставаться на экране. Точки с `collect_ok` истина MUST NOT получать этот баннер, даже если поля «не найдено».

#### Scenario: Одна точка упала при сборе
- GIVEN три записи, у второй `collect_ok` ложь, `collect_error` с типом исключения, title «Студия Б»
- WHEN показывают отчёт
- THEN есть баннер «Сбор точки Студия Б упал»
- THEN нет traceback в интерфейсе
- THEN таблица полей видна

#### Scenario: Честно пустые поля без сбоя
- GIVEN точка со всеми полями «не найдено» и `collect_ok` истина
- WHEN показывают отчёт
- THEN баннера падения сбора для этой точки нет

### Requirement: Нет reload модулей на rerun Streamlit
Точка входа Streamlit MUST импортировать пакетные модули один раз обычным import. Система MUST NOT вызывать `importlib.reload` для `collect`, `store`, `score`, `report`, `proxy` или `llm` на rerun. Система MUST NOT проверять наличие `as_sourced_field` / `coerce_place_record` / полей модели как повод перезагрузить модуль.

#### Scenario: Исходник app без reload
- GIVEN файл точки входа Streamlit
- WHEN его читают как текст
- THEN нет `importlib.reload`
- THEN нет проверки «нужен reload collect» по отсутствию хелперов или полей модели

#### Scenario: Rerun не меняет identity классов ради UI
- GIVEN приложение запущено
- WHEN Streamlit делает rerun после нажатия кнопки
- THEN таблица полей и карточки работают без принудительной перезагрузки модулей

### Requirement: Открытие сохранённого разбора одним бандлом
По кнопке «Открыть сохранённый» интерфейс SHALL загрузить строки, usage LLM и вердикт одним чтением payload (`load_run_bundle` или эквивалент). Система MUST NOT делать три отдельных чтения одного JSON ради строк, usage и вердикта.

#### Scenario: Кнопка открыть сохранённый
- GIVEN запись в SQLite с тремя точками, usage и вердиктом
- WHEN нажимают «Открыть сохранённый»
- THEN на экране таблица полей из этой записи
- THEN usage и вердикт в сессии совпадают с payload
- THEN загрузчик HTML не вызывается

### Requirement: Отчёт разделён на блоки и ограничен по ширине
После сбора или открытия сохранённого разбора интерфейс SHALL показать отчёт как отдельные блоки в таком порядке: карта (справочно), сравнение, карточки точек, вывод модели, расход. Карта MUST остаться справочной: MUST NOT влиять на поля, индекс и сохранённый payload. Основной контейнер отчёта SHALL иметь максимальную ширину около 1100px (узкая колонка по центру, не на всю `layout="wide"`). Баннер падения сбора точки MUST остаться видимым и MUST NOT прятаться внутри карты.

#### Scenario: Порядок блоков после сбора
- GIVEN три собранные точки
- WHEN показывают отчёт
- THEN на экране есть отдельные блоки карты, сравнения, карточек, вывода модели и расхода
- THEN карта подписана как справочная / только просмотр
- THEN блок сравнения идёт после карты и до карточек

#### Scenario: Ширина контейнера
- GIVEN открытый отчёт
- WHEN смотрят стили контейнера отчёта
- THEN max-width около 1100px
- THEN контент не растянут на всю ширину wide-layout без ограничения

### Requirement: Карточка точки из card_payload в expander
Для каждой точки отчёта интерфейс SHALL показать expander. Содержимое MUST строиться из существующего `card_payload` / `CardView` (те же поля, источники, список missing) и MUST NOT дублировать отдельную схему карточки. Пустое поле MUST отображаться как «не найдено», MUST NOT как ноль. Ссылка источника SHALL быть видна, если она есть в `CardView`. Список missing SHALL быть виден, если поля отсутствуют.

#### Scenario: Expander на каждую точку
- GIVEN три точки после сбора
- WHEN показывают блок карточек
- THEN три expander, по одному на точку
- THEN в каждом есть заголовок точки, поля с текстом значения, источники и список отсутствующих (если есть)

#### Scenario: Нет отдельной схемы карточки
- GIVEN код точки входа Streamlit
- WHEN рендерят карточку
- THEN вызывается существующий `card_payload`
- THEN нет второй структуры полей карточки рядом с `CardView`

### Requirement: Таблица сравнения с zebra, tabular-nums и лидерами
Блок сравнения SHALL показать таблицу полей точек. Строки MUST чередовать фон (zebra). Фон чередования MUST быть полупрозрачным относительно темы и MUST NOT затирать цвет текста: подписи полей и значения (включая «не найдено») SHALL оставаться читаемыми в светлой и тёмной теме Streamlit. Жёсткая светлая заливка вроде `#f6f7f9` MUST NOT использоваться. Числовые ячейки (в том числе индекс и баллы блоков) SHALL использовать табличные цифры (`tabular-nums` / `font-variant-numeric: tabular-nums`). Система SHALL отметить лидеров среди точек по блокам `PlaceScore.blocks` с именами `reputation`, `stability`, `location` (подписи: репутация, устойчивость, локация) и по индексу. Лидер — точка с максимальным числовым значением среди тех, у кого значение есть; при равенстве максимума лидерами SHALL быть все с этим значением. Точка без числа (нет данных / недостоверный индекс) MUST NOT быть лидером этого показателя.

#### Scenario: Zebra и табличные цифры
- GIVEN отчёт с таблицей сравнения
- WHEN смотрят разметку/стили таблицы
- THEN соседние строки поля отличаются фоном
- THEN числовые значения с `tabular-nums`

#### Scenario: Тёмная тема не прячет текст зебры
- GIVEN тёмная тема Streamlit и чётная строка таблицы
- WHEN смотрят ячейку «не найдено» или подпись поля
- THEN фон не светлая непрозрачная заливка `#f6f7f9`
- THEN текст остаётся видимым на фоне строки

#### Scenario: Один лидер по репутации
- GIVEN три точки, баллы репутации 3, 2 и 1, индексы 80, 50 и 40
- WHEN показывают сравнение
- THEN точка с 3 отмечена лидером репутации
- THEN точка с индексом 80 отмечена лидером индекса
- THEN две другие не лидеры этих показателей

#### Scenario: Ничья и пустой блок
- GIVEN две точки с баллом устойчивости 2 и третья без балла устойчивости
- WHEN показывают сравнение
- THEN обе с баллом 2 — лидеры устойчивости
- THEN точка без балла не лидер устойчивости

### Requirement: Прогресс сбора через st.status
Пока собирают поля точек, интерфейс SHALL показать `st.status` с текстом вида «точка i из n · этап», где i — номер текущей точки (с 1), n — число точек, этап — текущий шаг сбора этой точки. Система MUST NOT показывать единственный голый spinner с текстом «Собираем поля по трём точкам» как единственный индикатор этого этапа. Intake-spinner «Уточняем данные ...» и spinner ответа модели MAY остаться. После успеха статус MUST закрыться или перейти в complete, отчёт SHALL показаться.

#### Scenario: Сбор трёх точек
- GIVEN intake READY и три выбранные карточки
- WHEN идёт сбор полей
- THEN на экране status с «точка» , порядковым номером и «из» n
- THEN в тексте есть этап
- THEN нет единственного индикатора «Собираем поля по трём точкам»

#### Scenario: Исходник без голого collect-spinner
- GIVEN файл точки входа Streamlit
- WHEN его читают как текст
- THEN нет spinner-строки «Собираем поля по трём точкам»
- THEN есть `st.status` (или эквивалентный вызов status) для сбора

### Requirement: Правка ячейки сохраняется после смены раскладки
Человек MAY править значение поля из таблицы сравнения тем же диалогом, что сейчас. После «Сохранить» система SHALL обновить рабочий ряд в сессии, SHALL пересчитать индекс и SHALL записать разбор в SQLite (`update_run` / `save_run`, как сейчас). Раскладка блоков, CSS и карточки MUST NOT отменять это сохранение. Пометка «недостоверный» SHALL по-прежнему убирать числовой индекс.

#### Scenario: Сохранить правку рейтинга
- GIVEN открытый отчёт с сохранённым `run_id`
- WHEN человек меняет рейтинг в диалоге и нажимает «Сохранить»
- THEN в таблице новое значение
- THEN после rerun значение то же
- THEN payload разбора в SQLite содержит правку (полка слабо, источник «правка человека»)

#### Scenario: Карточки читают те же рабочие ряды
- GIVEN правка уже в `working_rows`
- WHEN показывают expander карточки этой точки
- THEN `card_payload` отражает исправленное поле, не сырой сбор до правки

### Requirement: Строки таблицы частичный масштаб и свежесть 2ГИС
Таблица сравнения SHALL включать строки для `twogis_last_review`, `twogis_reviews_90d`, `twogis_plus_minus`, `place_type`, `twogis_rubrics` и `twogis_price_level` (подписи в `FIELD_LABELS`). Пустое значение MUST отображаться как «не найдено», MUST NOT как ноль. Эти строки MUST NOT становиться новым блоком индекса 50/25/25 и MUST NOT получать отметку лидера как четвёртый блок формулы. Лидер по-прежнему только по `reputation`, `stability`, `location` и итоговому индексу. Карточка точки SHALL показывать те же поля, что таблица, через существующий `card_payload` / `FIELD_LABELS`.

#### Scenario: Новые строки в таблице
- GIVEN три собранные точки
- WHEN показывают блок сравнения
- THEN в таблице есть строки даты последнего отзыва, отзывов за 90 дней, плюс/минус, типа места, рубрик и уровня цен
- THEN нет колонки или бейджа «масштаб» как четвёртого блока индекса

#### Scenario: Честный прочерк свежести
- GIVEN у точки `twogis_last_review`, `twogis_reviews_90d` и `twogis_plus_minus` со статусом «не найдено»
- WHEN показывают таблицу
- THEN в ячейках «не найдено»
- THEN нет «0» и нет «нет данных» в виде нуля

#### Scenario: Нет лидера масштаба
- GIVEN три точки с разными `place_type` и рубриками
- WHEN отмечают лидеров сравнения
- THEN лидеры только репутация, устойчивость, локация и индекс
- THEN отдельного лидера «масштаб» нет
