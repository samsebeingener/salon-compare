## Purpose

Сбор открытых полей трёх точек: каскад API карт, затем один HTML, иначе «не найдено». Точки независимы. Капчу не обходим.

## Requirements

### Requirement: Каскад поля API затем HTML затем не найдено
Для каждого сравниваемого поля системы карт система SHALL сначала взять значение из JSON API 2ГИС. Система MUST NOT вызывать Яндекс Places / ППО (`search-maps.yandex.ru`) и MUST NOT хранить поля `yandex_*`. Если поля нет в ответе 2ГИС (пусто, нет ключа, ошибка запроса), система SHALL сделать не больше одного GET открытой HTML-страницы той же карточки 2ГИС. Если HTML не дал поле — значение MUST быть «не найдено», без нуля и без среднего. Сбор SHALL загружать карточку по идентификатору уже выбранной точки. Несколько результатов поиска на шаге зацепок MUST NOT превращаться в «не найдено» на шаге полей.

#### Scenario: Полный ответ API
- GIVEN фикстура API 2ГИС с рейтингом и числом отзывов
- WHEN собирают поля точки
- THEN рейтинг 2ГИС заполнен из API со ссылкой источника
- THEN HTML для этого поля не вызывается

#### Scenario: В API нет рейтинга, HTML отдал
- GIVEN API 2ГИС без рейтинга и HTML карточки с рейтингом
- WHEN собирают поля точки
- THEN рейтинг 2ГИС берётся из HTML со ссылкой страницы
- THEN поле не заполняется нулём

#### Scenario: API пусто и HTML закрыт
- GIVEN пустой API 2ГИС и HTML с капчей, логином или 403
- WHEN собирают поля точки
- THEN рейтинг и отзывы 2ГИС имеют пометку «не найдено»
- THEN значение не подменяется нулём или средним
- THEN защиту (капча/логин) не обходят повторными запросами

#### Scenario: Поиск нашёл несколько карточек
- GIVEN поиск по зацепке вернул больше одной карточки 2ГИС
- WHEN ещё нет подтверждения пользователя
- THEN поля не заполняются как «не найдено» из‑за числа хитов
- THEN сначала запрашивается подтверждение со ссылками

### Requirement: Три точки независимо
Сбой или пустые поля одной точки MUST NOT отменять сбор двух других. Система SHALL вернуть запись по каждой из трёх точек.

#### Scenario: Один источник молчит у одной точки
- GIVEN у первой точки API 2ГИС пуст, у второй и третьей API полон
- WHEN собирают три точки
- THEN первая точка остаётся в результате с дырками «не найдено» где пусто
- THEN вторая и третья точки собраны
- THEN запуск не останавливается целиком

### Requirement: Соседи в радиусе 500 м
Система SHALL собрать число похожих студий в ~500 м и одну строку: их средний рейтинг выше или ниже нашей точки. Сначала API радиуса по координатам точки; если поля нет — один GET HTML. Иначе «не найдено». Число соседей MUST NOT подменяться нулём, если данных нет. Запрос карточки 2ГИС SHALL включать координаты (`items.point`), если ключ позволяет.

#### Scenario: Соседи из API
- GIVEN API радиуса вернул число соседей и средний рейтинг выше нашей точки
- WHEN собирают поля точки
- THEN есть число соседей и пометка «выше»
- THEN HTML соседей не вызывается

#### Scenario: Соседей нет в API и HTML закрыт
- GIVEN API радиуса без числа соседей и HTML с 403
- WHEN собирают поля точки
- THEN соседи — «не найдено», не ноль

#### Scenario: Нет координат — соседи не рисуются
- GIVEN карточка без точки на карте
- WHEN собирают поля
- THEN соседи — «не найдено», не ноль

### Requirement: Сайт студии один GET
Если у точки есть URL сайта, система SHALL сделать один GET открытой страницы. Капча, логин-стена или 403 MUST дать «не найдено» для полей сайта. HTTP 404 MUST дать «не найдено». Успешный GET MAY заполнить краткое «о нас», если разбор HTML (схема Pydantic) это вернул. GET SHALL отправлять User-Agent браузера.

#### Scenario: Сайт открылся
- GIVEN URL сайта и HTML без защиты, парсер вернул текст «о нас»
- WHEN собирают поля точки
- THEN поле сайта заполнено со ссылкой на URL
- THEN повторного GET нет

#### Scenario: Сайт закрыт
- GIVEN URL сайта и ответ 403
- WHEN собирают поля точки
- THEN поле сайта — «не найдено»

#### Scenario: Сайт 404
- GIVEN URL сайта и ответ 404
- WHEN собирают поля точки
- THEN поле сайта — «не найдено»

### Requirement: Старый разбор без Яндекса
`load_run` SHALL открыть payload, в котором есть ключи `yandex_*` или их нет. Лишние ключи Яндекса MUST игнорироваться. Отсутствие полей Яндекса MUST NOT ронять разбор.

#### Scenario: Payload со старыми полями Яндекса
- GIVEN SQLite JSON точки с `yandex_rating` и без обязательности этих полей в текущей схеме
- WHEN открывают сохранённый разбор
- THEN запись загружается
- THEN колонок Яндекса в новой таблице нет

### Requirement: Оболочка реестра без идентификатора не заполняет поля
Если HTML реестра открылся, но в теле нет запрошенного ОГРН или ИНН, система MUST поставить «не найдено». Система MUST NOT выводить «есть дела», «не обнаружено», «банкротство» по общим словам оболочки (арбитраж, войти, торги).

#### Scenario: КАД отдал оболочку без ОГРН
- GIVEN HTML kad.arbitr.ru со словами «арбитраж» и «дела», без цифр ОГРН
- WHEN собирают юрполя по этому ОГРН
- THEN КАД — «не найдено»
- THEN значение не «есть дела»

#### Scenario: ЕГРЮЛ-капча без ОГРН в теле
- GIVEN HTML ЕГРЮЛ со словом captcha и без ОГРН
- WHEN собирают юрполя
- THEN поля ЕГРЮЛ — «не найдено»

### Requirement: ИНН не подменять ОГРН в Федресурсе и КАД
Федресурс и КАД MUST вызываться только с ОГРН (13 или 15 цифр). ИНН (10 или 12 цифр) MAY идти только в поиск ЕГРЮЛ.

#### Scenario: На карте только ИНН
- GIVEN карточка с ИНН без ОГРН
- WHEN собирают юрполя
- THEN запроса Федресурса и КАД с этим ИНН нет

### Requirement: Слово войти не закрывает страницу
Классификация HTML SHALL считать страницу закрытой при 401/403/429 или маркере капчи. Слово «войти» в меню MUST NOT само по себе давать статус закрыто.

#### Scenario: Сайт 200 с кнопкой Войти
- GIVEN HTML статус 200 с текстом «Войти» и без капчи
- WHEN классифицируют ответ
- THEN статус не blocked

#### Scenario: 403 остаётся закрытым
- GIVEN HTML статус 403
- WHEN классифицируют ответ
- THEN статус blocked

### Requirement: Fallback ЕГРЮЛ через DuckDuckGo и карточку rusprofile
Если у точки есть ровно один ОГРН и официальный HTML ЕГРЮЛ не дал дату, статус и вид деятельности, система SHALL сделать один GET HTML-поиска DuckDuckGo без API-ключа по запросу этого ОГРН и `site:rusprofile.ru/id`. Система SHALL открывать найденные URL вида `rusprofile.ru/id/{цифры}` по очереди, не больше пяти. Значение MUST попасть в отчёт только если тело карточки содержит этот ОГРН. Первую ссылку выдачи без сверки брать MUST NOT. Поля MUST иметь полку «слабо» и ссылку на карточку rusprofile, не на DuckDuckGo. Система MUST NOT снимать учредителей и ФИО. Федресурс и КАД MUST NOT заполняться из страницы rusprofile. Капча или 403 на поиске или карточке MUST дать «не найдено» для этих полей ЕГРЮЛ; защиту не обходить повторными запросами. Если официальный ЕГРЮЛ уже заполнил хотя бы одно поле, поиск DuckDuckGo MUST NOT вызываться.

#### Scenario: ЕГРЮЛ пуст, поиск и карточка совпали по ОГРН
- GIVEN ОГРН `1147746349552`, официальный ЕГРЮЛ без полей, фикстура DuckDuckGo со ссылкой `rusprofile.ru/id/7301223` и HTML карточки с этим ОГРН, датой, статусом и видом деятельности
- WHEN собирают юрполя
- THEN дата, статус и вид деятельности заполнены
- THEN источник — URL карточки rusprofile
- THEN полка поля — слабо
- THEN Федресурс и КАД не берутся из этой карточки

#### Scenario: Первая ссылка без ОГРН, вторая с ОГРН
- GIVEN выдача DuckDuckGo с двумя `/id/`, первая карточка без запрошенного ОГРН, вторая с ОГРН и полями
- WHEN собирают юрполя
- THEN поля берутся со второй карточки
- THEN первая карточка не становится источником

#### Scenario: Капча DuckDuckGo
- GIVEN официальный ЕГРЮЛ пуст и HTML DuckDuckGo со статусом закрыто (капча)
- WHEN собирают юрполя
- THEN поля ЕГРЮЛ — «не найдено»
- THEN запросов rusprofile нет
- THEN капчу не решают и не повторяют поиск

#### Scenario: Официальный ЕГРЮЛ уже отдал поля
- GIVEN HTML ЕГРЮЛ с ОГРН и заполненными полями
- WHEN собирают юрполя
- THEN источник полей ЕГРЮЛ — страница ФНС
- THEN DuckDuckGo не вызывается

### Requirement: Пауза между запросами DuckDuckGo и rusprofile
Между GET HTML-поиска DuckDuckGo и GET карточек rusprofile система SHALL выдерживать паузу в секундах (не ноль в приложении). Один объект паузы MUST действовать на все три точки одного прогона. В тестах пауза подменяется: реальной сети и реального sleep нет. Капчу пауза не обходит и не решает.

#### Scenario: Два paced-запроса подряд
- GIVEN fallback: сначала DuckDuckGo, затем одна карточка rusprofile
- WHEN собирают юрполя
- THEN между этими GET зафиксирована одна пауза
- THEN тест не вызывает сетевой sleep

#### Scenario: Три салона делят паузу
- GIVEN три точки с ОГРН и пустым официальным ЕГРЮЛ
- WHEN собирают три точки
- THEN паузы идут по цепочке запросов всех трёх точек, не с нуля на каждом салоне

### Requirement: DuckDuckGo HTML-поиск через POST
Запрос HTML-поиска DuckDuckGo (`html.duckduckgo.com`) SHALL выполняться методом POST с полем `q`, без GET той же страницы. Капчу MUST NOT решать. Если POST закрыт или пуст — поля ЕГРЮЛ с этого шага «не найдено».

#### Scenario: URL поиска DuckDuckGo уходит POST
- GIVEN URL `https://html.duckduckgo.com/html/?q=…`
- WHEN загрузчик открывает этот URL
- THEN вызывается POST с телом формы, содержащим исходный `q`
- THEN GET этой страницы не вызывается

### Requirement: JSON has_captcha не закрывает открытую карточку
Классификация HTML MUST NOT ставить «закрыто» только из‑за JSON-ключей `has_captcha` / `disable_captcha`. HTTP 200 с карточкой компании и этими ключами SHALL быть «ok». Маркер реальной капчи (`smartcaptcha`, `recaptcha`, `g-recaptcha`) или 401/403/429 MUST оставаться «закрыто».

#### Scenario: rusprofile с has_captcha в JSON
- GIVEN HTML статус 200, в теле ОГРН и «Действующая организация», в JSON `"has_captcha":true`
- WHEN классифицируют ответ
- THEN статус ok

#### Scenario: Настоящая smartcaptcha
- GIVEN HTML статус 200 со словом smartcaptcha
- WHEN классифицируют ответ
- THEN статус blocked

### Requirement: Статус и ОКВЭД с карточки, не с связей и меню
Разбор ЕГРЮЛ SHALL считать организацию действующей, если на карточке «действующая организация», даже если ниже есть «ликвидированных связанных организаций». Вид деятельности SHALL браться из «основной вид деятельности», не из первого «оквэд» в меню.

#### Scenario: Связанные ликвидированы, сама действует
- GIVEN HTML с «Действующая организация», датой регистрации, «Основной вид деятельности Предоставление услуг парикмахерскими» и фразой «ликвидированных связанных организаций», плюс «оквэд» в меню раньше по тексту
- WHEN разбирают ЕГРЮЛ
- THEN статус «действует»
- THEN деятельность содержит парикмахерскими
- THEN деятельность не из меню оквэд

### Requirement: РБК Компании по ОГРН, если ЕГРЮЛ пуст
Если официальный ЕГРЮЛ не дал дату, статус и деятельность, система SHALL сделать один GET `https://companies.rbc.ru/search/?query={ОГРН}`. Поля MUST браться только из блока карточки, где есть этот ОГРН. Заголовок выдачи с тем же ОГРН MUST NOT считаться карточкой. Полка MUST быть «слабо», источник — URL поиска. Федресурс и КАД MUST NOT заполняться с РБК. Учредителей и ФИО MUST NOT копировать. Если карточки нет или страница закрыта, система MAY дальше искать через DuckDuckGo→rusprofile. Капчу MUST NOT решать. Если официальный ЕГРЮЛ уже заполнил поля, GET РБК MUST NOT вызываться.

#### Scenario: ЕГРЮЛ пуст, РБК отдал карточку
- GIVEN ОГРН `1147746349552`, ЕГРЮЛ закрыт, HTML поиска РБК с `company-card`, статусом «Действует», датой регистрации `01.04.2014` и тем же ОГРН
- WHEN собирают юрполя
- THEN статус «действует», дата `01.04.2014`, полка слабо, источник URL поиска РБК
- THEN DuckDuckGo и rusprofile не вызываются

#### Scenario: В выдаче только заголовок запроса
- GIVEN HTML поиска РБК с текстом «Результаты по запросу» и ОГРН, без блока карточки с этим ОГРН
- WHEN собирают юрполя
- THEN поля с РБК не заполнены
- THEN допускается следующий шаг rusprofile

#### Scenario: Официальный ЕГРЮЛ уже есть
- GIVEN ЕГРЮЛ вернул карточку с ОГРН
- WHEN собирают юрполя
- THEN URL поиска РБК не вызывается
