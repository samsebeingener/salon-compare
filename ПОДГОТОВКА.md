# Подготовка: сравнение трёх маникюрных точек Москвы

Документ **утверждён** 2 сентября 2026. Подготовка закрыта. Код — только по отдельной команде.

Дата: 2 сентября 2026.

## 1. Задача своими словами

Инвестор смотрит на три действующие маникюрные точки в Москве и хочет понять: **какую смотреть первой как объект покупки и почему**.

Цены сделки и внутренней бухгалтерии нет. Смотрим только открытые данные: сайт, карты, отзывы, реестр юрлиц.

На вход — три «зацепки», по одной на салон. Это может быть сайт, название, ОГРН или обрывок текста. На выход — сравнительный отчёт: одинаковые поля по трём точкам, оценка привлекательности, честная пометка «найдено / слабо / не найдено», короткий вывод.

## 2. Что на самом деле проверяют

Не «сколько кода написано». Проверяют:

- умеем ли собрать разношёрстные данные в одну таблицу;
- отделяем ли факт от догадки;
- не падает ли разбор, если один салон «ломается»;
- можно ли объяснить вывод вслух за 30 минут;
- виден ли процесс: OpenSpec (замысел) и TDD (тест раньше кода);

## Сверка с заданием (2 сентября 2026)

Ниже — что в задании обязательно, и есть ли это у нас. Пропуски как у OpenSpec: в подготовке должны быть видны, даже если код ещё не пишем.

### Есть, совпадает

- три зацепки → сбор → оценка → сравнительный отчёт;
- открытые данные, без цены сделки;
- одни и те же признаки, дырки честно пустые;
- источник или «не найдено» / «не подтверждено»;
- вывод модели только по уже посчитанным цифрам;
- OpenSpec: сначала «дано / когда / тогда»;
- TDD: тест красный раньше кода, в истории git это видно;
- не платформа, не инвестсовет, не закрытые данные, не обход защиты.

### Было слабо или не записано — фиксируем сейчас

| Требование задания | Как делаем |
|---|---|
| География | Москва и ближайшее Подмосковье в пределах МЦД |
| Типы зацепок | Не только сайт / название / ОГРН. Ещё: ИНН, ссылка на карты или запись, обрывок свободного текста. Приложение само понимает, что ему дали |
| Модель внутри приложения | Не «свободный рассказ», а строгая схема (Pydantic). Плохой ответ: повтор / отказ, приложение не падает. Провайдер меняется настройкой, не правкой логики |
| Ключи | Только в `.env`, в git не попадают. В репозитории образец `.env.example`. Ключ не на экране, не в логах, не в образе Docker. Если LLM из РФ недоступен — в `.env` задают `HTTP_PROXY` и `HTTPS_PROXY` |
| Сохранение | Весь запуск пишется в SQLite (файл рядом с проектом, в git не кладём). Старый отчёт открывается без ключа |
| Пометка «недостоверный» | Можно исправить поле **и** пометить весь объект как недостоверный — отчёт пересчитывается |
| Стек | Python 3.12+, один процесс, SQLite, веб — Streamlit (уже в правилах агента; задание разрешает и другие) |
| Запуск | Docker + `docker compose`. Одна команда. GitHub Actions: проверка качества, тесты, сборка образа с номером коммита, контейнер поднялся |
| Проверки | Линтер, типы, тесты — **одной командой** и у нас, и на GitHub. Тесты в интернет не ходят: ответы модели и страницы — заготовки |
| README | Что делает, как запустить, как устроены куски, что храним, почему так, что за рамками. Отдельным абзацем: какой агент и какие модели, что агент сделал сам и почему оставили |
| Вывод в интерфейсе | Помечен как текст модели, не как совет «покупай» |

### Сознательно уже, чем минимум задания

- две карты, число отзывов, плюс/минус если есть, в баллы — более свежий источник;
- Федресурс и арбитраж для устойчивости.

### Дырки задания — закрыты решением

1. **Соседи.** Число студий в ~500 м **и** одна строка: их средний рейтинг выше или ниже нашей точки. Без разбора каждого соседа.
2. **Попадание в сравнение.** Любая зацепка ок, даже голый ОГРН. Неопознали однозначно — спрашиваем. Дырки в таблице честно пустые, салон из тройки не выкидываем молча.
3. **Две зацепки — один салон.** Сообщаем «это одна точка» (со ссылками) и просим заменить одну из трёх зацепок. Не сравниваем объект с самим собой.
4. **Динамика отзывов.** Есть ли отзывы за последние 90 дней (да/нет) и дата последнего. График по месяцам не строим.

## Как обязаны работать — OpenSpec

Это не «документация потом», а **правило задания**. Репозиторий и описание процесса: [github.com/Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec).

Простыми словами: любая заметная возможность сначала описывается как изменение (что хотим получить), со сценариями вида **«дано / когда / тогда»**. Код пишется только после этого. Когда возможность сдана, описание уходит в архив — по репозиторию видно, что задумали **до** кода, а не придумали задним числом.

Одна возможность — одно изменение OpenSpec — одна ветка — один pull request. Как после сценария появляется код — в следующем блоке (TDD).

Шесть сценариев из раздела 11 — заготовка именно для OpenSpec. Сами файлы OpenSpec появятся в репозитории, когда скажешь «можно разрабатывать». Пока код не пишем.

## Как обязаны работать — TDD (test-first)

Это **не часть OpenSpec**, а второе правило задания. OpenSpec отвечает на вопрос «что должно получиться». TDD — на вопрос «в каком порядке появляется код».

Простыми словами:

1. Берём сценарий из OpenSpec.
2. Пишем проверку (тест), которая **ещё не проходит** — «красный».
3. Эту проверку **сохраняем в git отдельно и раньше**, чем рабочий код — в истории должно быть видно, что сначала было «не работает».
4. Только потом пишем код, пока проверка не станет «зелёной».
5. Подчищаем, не раздувая.

Без этого шага «тест раньше кода» работу не примут, даже если OpenSpec лежит в репозитории.

## 6. Какие признаки сравниваем

Одинаковый список для всех трёх:

- **Место:** район / метро, тип (улица, ТЦ, ЖК).
- **Масштаб:** сколько мастеров или кресел (если видно), часы, услуги, уровень цен.
- **Репутация:** рейтинг Яндекса **и** рейтинг 2ГИС (оба в отчёте), сколько отзывов всего, сколько плюсов и минусов (если площадка это отдаёт), дата последнего отзыва, есть ли отзывы за 90 дней. В индекс привлекательности берём более свежий источник. Нет разбивки плюс/минус — «не найдено», не выдумываем.
- **Соседи:** сколько похожих студий в ~500 м и одна строка — их средний рейтинг выше или ниже нашей точки.
- **Юрлицо:** возраст и статус — только если удалось связать точку с записью в реестре.
- **Источник** каждого значения + пометка достоверности.

Если поля нет — пишем «не найдено». Не подставляем ноль и не «рисуем среднее».

## 7. Как считаем привлекательность

Одна линейка на все три точки. Считаем **здоровье бизнеса**, не прибыль. Индекс примерно 0–100.

Четыре блока (твоя готовая логика, с двумя поправками ниже):

| Блок | Вес | Баллы |
|---|---|---|
| Репутация | 40% | В отчёте **всегда оба** значения: Яндекс и 2ГИС (рейтинг, число отзывов, плюс/минус если есть). В баллы идёт **более свежий** источник (чья лента отзывов новее). Шкала: >4.5 и много свежих +3; 4.0–4.5 +2; мало/старые +1; много негатива 0. Не усредняем две карты и не берём «красивую» цифру. Не ясно, какая свежее — в баллы не гадаем, пишем «не ясно какой свежее» |
| Устойчивость | 25% | >5 лет +3; 3–5 лет +2; <1 года +1. Нет судов/банкротства у **компании** +1; есть иски/банкротство −2. Считаем только если Федресурс и kad.arbitr открылись |
| Локация | 20% | ТЦ с проходимостью +3; первая линия улицы +2; двор ЖК +1; промзона 0. Соседи: число в 500 м + строка «их рейтинг выше/ниже». В вес локации число соседей не входит отдельным процентом |
| Масштаб | 15% | 5+ мастеров и полный прайс +3; 2–4 мастера +2; один мастер «на дому» −1 |

Поправки к сырой схеме:

1. **Нет данных ≠ ноль и ≠ «долгов нет».** Задание это прямо запрещает. Не нашли суды — блок устойчивости без штрафа и без бонуса.
2. **Соседи** видны в таблице (число + выше/ниже по рейтингу), но не пятый вес в формуле.
3. **Две карты:** в отчёте обе цифры; в индекс — только более свежие данные. Среднее из Яндекса и 2ГИС не считаем.

Итог — ориентир, не совет «покупай». В отчёте это сказано прямо.

## 8. Когда данным можно верить

Три полки, без серой каши:

- **Подтверждено** — значение есть в первоисточнике, ссылка открывается.
- **Слабо / не подтверждено** — источник один, даты отзывов нет, или две карты сильно расходятся.
- **Не найдено** — честно пусто.

Два рейтинга в отчёте не схлопываем в одну цифру. Для баллов выбираем более свежий; расхождение всё равно видно в таблице.

Модель (нейросеть) имеет право ошибиться. Человек может поправить цифру руками — отчёт пересчитывается.

## 9. Как выглядит отчёт

1. **Таблица:** три колонки (салоны), строки — признаки. Рейтинг Яндекса и рейтинг 2ГИС — **две отдельные строки**, не одна «средняя». Цветом/подписью видно: подтверждено / слабо / нет. Для баллов подписано, чей источник свежее.
2. **Карточка салона:** все поля, ссылка на источник, список «не нашли».
3. **Вывод:** какая точка интереснее, чем лучше двух других, при каком условии вывод сломается. Пишется моделью **по уже посчитанным цифрам**. В интерфейсе явно: «текст модели, не инвестиционный совет».
4. **Расход:** сколько токенов и примерно сколько денег стоил запуск.

## 10. Что сознательно не делаем

- платформу, логины, очереди, микросервисы;
- оценку «купи вот это, будет прибыль»;
- сбор закрытых данных;
- сравнение целой сети из 20 точек с одной студией так, будто это одно и то же;
- Instagram, Google Карты, фото, ФССП по людям, платный Youscan.

## 11. Сценарии (ещё не код)

Что должно происходить. Если что-то из этого не так — правим до разработки.

1. **Обычный запуск.** Ввёл три разные зацепки (сайт, название, ОГРН) → получил таблицу, три карточки, индекс и короткий вывод, у каждого поля — ссылка или «не найдено».
2. **Несколько похожих салонов.** Название/адрес/ОГРН тянут больше одной точки или данные перемешались → **не выбираем сами**. Показываем список кандидатов со ссылками на источники и просим подтвердить, какую точку разбирать.
3. **Один источник молчит.** Яндекс не открылся, 2ГИС открылся → салон всё равно в отчёте, дырки честно пустые, два других салона не отменяются.
4. **Нет ОГРН.** У точки только сайт, юрлицо не связали → устойчивость не считаем (не пишем «долгов нет»), остальные блоки считаем.
5. **Старый отчёт.** Открыл сохранённый разбор без ключа нейросети → таблица на месте, нового поиска нет.
6. **Ошибка модели.** Нейросеть выдала ерунду → приложение не падает, значение можно поправить руками, баллы пересчитываются.
7. **Недостоверный объект.** Человек помечает салон целиком как «данным нельзя верить» → индекс пересчитывается, салон в таблице остаётся с пометкой.
8. **Непонятная зацепка.** Вставили ИНН, ссылку на карту или обрывок текста → приложение распознаёт тип и идёт дальше или просит уточнить.
9. **Две зацепки — одна точка.** Сайт и ОГРН (или любые две) оказались одним салоном → не сравниваем сами с собой, просим заменить одну зацепку, показываем ссылки.
